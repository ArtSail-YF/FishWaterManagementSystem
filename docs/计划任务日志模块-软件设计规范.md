# 计划任务日志模块 - 软件设计规范

> 版本: 1.0 | 最后更新: 2026-05-29 | 状态: 评审中

---

## 1. 模块概述

### 1.1 业务定位

计划任务日志（简称任务日志）是水产养殖生产管理系统的核心数据组件，位于"计划-任务-日志"三条数据的下游：

```
生产计划 (prod_plan) → 生产任务 (prod_task) → 生产日志 (prod_log)
```

日志记录了生产任务在执行过程中的**实际发生数据**，是对计划与任务的执行反馈，也是后续统计分析与审计追溯的基础数据源。

### 1.2 核心职责

| 职责 | 说明 |
|------|------|
| 执行记录 | 记录工人对任务的执行结果，包括时间、数量、位置等 |
| 操作追溯 | 留存完整的操作人、操作时间、位置信息，满足食品安全溯源要求 |
| 数据对账 | 实际执行数据与计划数据的偏差分析基础 |
| 统计支撑 | 为产量统计、用料统计、工时统计等提供原始数据 |
| 合规审计 | 记录药物使用、投喂操作等关键操作，满足监管部门审查要求 |

### 1.3 目标用户

| 角色 | 操作场景 |
|------|----------|
| 一线工人 | 通过 App 打卡执行任务、上传照片、记录实际用量 |
| 养殖场管理员 | 查询日志、审核数据、补录遗漏记录 |
| 现场主管 | 查看执行情况、统计分析、异常处理 |
| 质检/审计 | 追溯操作历史、查看药物使用记录 |

## 2. 领域模型

### 2.1 实体关系

```
┌─────────────────┐      ┌─────────────────┐      ┌─────────────────┐
│    ProdPlan     │      │    ProdTask     │      │    ProdLog      │
│   (生产计划)     │──1:N→│   (生产任务)     │──1:N→│   (生产日志)     │
│                 │      │                 │      │                 │
│ - title         │      │ - taskTitle     │      │ - taskId        │
│ - planType      │      │ - status        │      │ - planId        │
│ - startTime     │      │ - actionTime    │      │ - actionTime    │
│ - endTime       │      │ - assigneeId    │      │ - quantity      │
│ - status        │      │ - deadlineTime  │      │ - photoUrls     │
└─────────────────┘      └─────────────────┘      │ - gpsLat/Lng   │
                                                   │ - verifyStatus │
                                                   └─────────────────┘
```

### 2.2 ProdLog 实体定义

| 字段 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| id | BIGINT (PK) | Y | 自增 | 主键 |
| taskId | BIGINT | N | null | 关联任务ID，可为空（允许管理员直接录入日志） |
| planId | BIGINT | N | null | 关联计划ID，冗余字段便于跨任务查询 |
| baseId | BIGINT | N | null | 所属基地ID，冗余字段 |
| targetType | VARCHAR(20) | N | null | 目标类型: pond(塘口) / cage(网箱) / vsl(工船) |
| targetId | BIGINT | N | null | 目标实体ID |
| logType | VARCHAR(50) | N | null | 作业类型: feed(投喂) / medicine(用药) / harvest(收获) / maintenance(维护) |
| actionTime | DATETIME | Y | 当前时间 | 实际执行时间 |
| quantity | DECIMAL(18,3) | N | null | 实际数量/用量 (单位由logType决定) |
| photoUrls | TEXT | N | null | 照片URL列表，多个用逗号分隔 |
| gpsLat | DECIMAL(10,7) | N | null | 打卡纬度（WGS84坐标系） |
| gpsLng | DECIMAL(10,7) | N | null | 打卡经度 |
| source | VARCHAR(20) | Y | 'app' | 来源: app(APP录入) / admin(后台录入) / system(系统自动) |
| createdBy | BIGINT | N | null | 录入人账号ID |
| actualWorkerId | BIGINT | N | null | 实际执行工人ID（可与录入人不同） |
| isBackfilled | TINYINT(1) | N | 0 | 是否事后补录: 0-实时记录, 1-补录 |
| backfillReason | VARCHAR(500) | N | null | 补录原因 |
| verifyStatus | VARCHAR(20) | N | 'auto' | 审核状态: auto(自动通过) / pending(待审核) / rejected(已驳回) |
| createTime | DATETIME | Y | 当前时间 | 创建时间 |
| updateTime | DATETIME | Y | 当前时间 | 更新时间 |
| isDelete | TINYINT(1) | Y | 0 | 逻辑删除标记 |
| deleteTime | DATETIME | N | null | 删除时间 |

### 2.3 枚举定义

#### logType 作业类型

| 编码 | 名称 | 说明 |
|------|------|------|
| feed | 投喂 | 投放饲料操作 |
| medicine | 用药 | 防治用药操作 |
| harvest | 收获 | 捕捞/收获操作 |
| maintenance | 维护 | 设施维护操作 |
| water_change | 换水 | 换水/增氧操作 |
| seeding | 放苗 | 投放苗种操作 |
| inspection | 巡检 | 日常巡检操作 |
| other | 其他 | 其他类型操作 |

#### source 来源

| 编码 | 名称 | 触发场景 |
|------|------|----------|
| app | APP录入 | 工人通过手机APP打卡 |
| admin | 后台录入 | 管理员在Web后台录入或补录 |
| system | 系统自动 | IoT设备自动触发或定时任务生成 |

#### verifyStatus 审核状态

| 编码 | 名称 | 说明 |
|------|------|------|
| auto | 自动通过 | APP打卡默认自动通过 |
| pending | 待审核 | 后台录入或补录默认待审核 |
| rejected | 已驳回 | 审核不通过 |

### 3.2 详细用例

#### UC-001: 工人打卡执行任务

| 项目 | 内容 |
|------|------|
| 参与者 | 一线工人 (通过App) |
| 前置条件 | 工人已登录且已被分配任务（assigneeId = 当前用户） |
| 触发条件 | 工人点击"开始执行"或"打卡完成" |
| 基本流程 | 1. 系统展示待执行任务列表 |
| | 2. 工人选择任务，进入执行页面 |
| | 3. 工人填写实际用量、拍摄照片 |
| | 4. 系统自动获取GPS位置 |
| | 5. 工人提交，系统创建ProdLog记录 |
| | 6. 系统更新对应ProdTask状态为'done' |
| | 7. 若任务关联Plan且所有子任务完成，触发计划状态更新 |
| 后置条件 | 生产日志创建成功，任务标记为已完成 |
| 业务规则 | R001: 每个任务每类操作一天最多记录一次 |
| | R002: GPS位置必须在中国渔业水域范围内 |
| | R003: 照片至少上传1张（用药类型强制，其他类型可选） |

#### UC-002: 管理员后台手动录入日志

| 项目 | 内容 |
|------|------|

| 基本流程 | 1. 管理员进入日志管理页面，点击"新增" |

| | 3. 填写作业类型、用量、时间、执行人等信息 |
| | 4. 上传照片（可选） |
| | 5. 提交，系统创建ProdLog，verifyStatus默认为'pending' |
| 后置条件 | 日志写入，等待审核 |
| 业务规则 | R004: 不关联任务的日志为"独立日志"，用于记录计划外的操作 |
| | R005: 后台录入的日志默认为待审核状态 |

#### UC-003: 事后补录日志

| 项目 | 内容 |
|------|------|
| 参与者 | 管理员（补录场景） |
| 前置条件 | 存在未记录执行数据的已完成/过期任务 |

#### UC-004: 审核日志

| 项目 | 内容 |
|------|------|

| 参与者 | 全部用户 |
| 关联用例 | UC-001, UC-002, UC-003 |
| 说明 | 日志照片作为执行证据统一管理，支持上传、预览、删除 |

| 项目 | 内容 |

| 统计指标 | 投喂总量(kg)、用药总量(kg)、收获总量(kg)、执行次数、工时统计 |
| 报表类型 | 日报: 按日期和执行人聚合 |
| | 周报/月报: 按周期聚合，含同比环比 |
| | 类型分布: 按logType统计占比 |
| | 个人绩效: 按执行人统计工作量 |

## 4. 业务逻辑与状态机

### 4.1 日志创建时的数据自动填充

当通过 App 从任务创建日志时，系统自动继承以下字段：

```
taskId    → 当前任务ID
planId    → 任务关联的planId
baseId    → 任务关联的baseId
targetType → 任务关联的targetType
targetId  → 任务关联的targetId
logType   → 任务的planType
createdBy → 当前登录用户ID
actualWorkerId → 当前登录用户ID（若任务有assignee则取assignee）
```

### 4.2 日志审核状态机

```
                    ┌─────────────┐
                    │    auto     │ ← 默认状态
                    │  (自动通过)  │
                    └──────┬──────┘
                           │
              ┌────────────┼────────────┐
              │ 后台审核驳回 │            │
              ▼             │            │
         ┌──────────┐      │            │
         │ rejected │──────┘   ┌────────┴────────┐
         │  (已驳回) │ 重新提交 │    pending      │
         └──────────┘         │   (待审核)      │
                               └─────────────────┘
                                       │
                                       │ 审核通过
                                       ▼
                               ┌──────────────┐
                               │    auto       │
                               │  (审核通过)    │
                               └──────────────┘
```

### 4.3 任务状态联动规则

```
日志创建 → 任务状态变更:

条件                                   | 任务目标状态
---------------------------------------|---------------
任务下所有日志创建完成（按actionTime）   | done
任务截至时间已过且无日志                | expired
任务被管理员主动取消                    | skipped
管理员补录日志（isBackfilled=true）     | done（即使已expired也可转为done）
```

### 4.4 关键业务规则详细说明

**R001 - 每天每任务单类型单次记录限制**
- 适用范围: App打卡场景
- 规则: 同一 taskId 在同一自然日（00:00:00 - 23:59:59）只能有一条 logType 匹配的日志
- 异常处理: 若重复打卡，前端提示"今日该任务已记录，是否修改？"跳转编辑

**R003 - 用药类型照片强制上传**
- 适用范围: logType='medicine'
- 规则: 创建日志时 photoUrls 不能为空
- 原因: 药物使用记录需留证以备食品安全追溯

**R004 - 独立日志规则**
- 适用范围: 未关联taskId的日志
- 说明: 允许管理员创建不关联任务的独立日志，用于记录临时性操作
- 限制: 独立日志必须指定baseId、targetType、targetId

## 6. 异常处理

### 6.1 错误码定义

| 错误码 | 说明 | 处理方式 |
|--------|------|----------|
| A0400 | 请求参数校验失败 | 前端展示具体字段错误 |
| A0401 | 照片上传失败 | 提示重新上传 |
| A0420 | 重复打卡 | 提示"今日已打卡"，跳转编辑 |
| A0421 | 用药记录无照片 | 提示"用药记录必须上传照片" |
| A0422 | GPS不在合法范围 | 提示重新获取位置或手动输入 |
| A0430 | 审核的日志不存在 | 返回404 |
| A0431 | 审核的日志已审核 | 提示"该日志已审核" |
| A0423 | 关联任务状态异常 | 提示"该任务已关闭，无法记录" |
| A0500 | 内部服务器错误 | 统一错误提示页面 |

### 6.2 一致性保证

1. **事务性**: 日志创建 + 任务状态更新须在同一数据库事务中
2. **幂等性**: 同一请求重复提交不产生重复记录（基于taskId+actionTime日期唯一约束）
3. **并发控制**: 使用乐观锁（updateTime字段）防止并发审核冲突

### 6.3 数据归档策略

| 时间范围 | 存储位置 | 查询方式 |
|----------|----------|----------|
| 0-6个月 | 主库(prod_log表) | 在线实时查询 |
| 6-24个月 | 历史归档表(prod_log_archived) | 归档表查询 |
| >24个月 | 冷存储(OSS/备份) | 线下导出 |

归档触发: 每月1日凌晨自动将超过6个月的日志迁移至归档表。

## 7. 安全与权限

### 7.1 数据隔离

- 工人只能查看和自己相关的日志（taskId关联的任务中assigneeId=当前用户）
- 管理员可查看所属基地下的全部日志
- 跨基地数据隔离通过baseId字段控制

### 7.2 操作权限矩阵

| 操作 | 工人 | 管理员 | 主管 | 审计 |
|------|------|--------|------|------|
| 创建日志(App) | Y | - | - | - |
| 创建日志(后台) | - | Y | Y | - |
| 修改日志 | - | Y(仅未审核) | Y(仅未审核) | - |
| 审核日志 | - | Y(same基地) | Y | - |
| 删除日志 | - | Y | Y | - |
| 查看日志详情 | Y(本人) | Y | Y | Y |
| 统计查询 | - | Y | Y | Y |
| 日志导出 | - | Y | Y | Y |

### 7.3 数据完整性

1. **不可篡改**: 已审核通过的日志不允许修改（包括内容和照片）
2. **删除约束**: 日志采用逻辑删除(isDelete字段)，保留所有历史数据
3. **操作审计**: 所有日志的创建、修改、审核操作均写入操作审计表

## 9. 非功能性需求

### 9.1 性能

| 指标 | 目标值 |
|------|--------|
| 日志列表查询 | < 500ms （百万级数据量） |
| 单条日志写入 | < 200ms |
| 统计查询 | < 2s |
| 照片上传 | 支持断点续传，单张<5MB |
| 并发支持 | 单基地200人同时打卡 |

### 9.2 优化策略

1. **索引设计**:
   - 联合索引 (baseId, logType, actionTime)
   - 联合索引 (taskId, actionTime)
   - 单列索引 (actualWorkerId, isDelete)

2. **查询优化**:
   - 统计查询使用物化视图或定时汇总表
   - 照片URL不存储在业务表，使用单独的照片存储表
   - 超过百万行考虑按baseId分区

3. **缓存策略**:
   - 统计概览数据: Redis缓存，TTL 5分钟
   - 最近7天日志: Redis缓存列表，TTL 1小时

### 9.3 接口限流

| 接口 | 限流策略 |
|------|----------|
| POST /api/log | 每人每秒1次 |
| POST /api/log/{id}/photos | 每人每分钟10次 |
| POST /api/log/search | 每人每秒5次 |

CREATE TABLE prod_log (
